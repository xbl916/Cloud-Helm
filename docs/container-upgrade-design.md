# 容器升级、维护与三版本回滚设计

## 目标

Cloud Helm 的模块镜像发布需要同时管理运行中的容器、宿主机 Compose 配置、
统一网关路由和 ACS 弹性容量，并满足以下要求：

1. 更新镜像 Tag 后同步更新设备上的 Docker Compose 文件。
2. 当前版本之外，至少保留最近三个成功版本作为可回滚目标。
3. 单本地实例先创建旧版本升级保护实例，多本地实例严格逐个排空升级。
4. 升级保护弹性与高负载弹性分别计算、分别记录事件。
5. 支持手工进入维护状态，供运维人员登录服务器修改 Compose。

升级实施必须遵循“先准备新版本，再切换运行版本”的原则。目标镜像拉取、
Compose 定位和配置校验均在停止旧容器前完成，不允许先停止容器或释放 GPU
再准备升级内容。

## 核心数据模型

一次升级或回滚对应一张独立发布单 `image_releases`，记录源版本、目标版本、
当前阶段、操作人、错误和时间。每个本地实例对应一条
`image_release_steps`，用于展示排空、切换和验证进度。

每次成功发布写入 `service_image_versions`。系统保留完整发布历史，并保证当前
版本之前最近三个成功版本可以直接发起回滚。回滚本身也创建新发布单，执行
与升级相同的安全流程。

现有 `scaling_services.release_*` 字段在迁移期间作为当前任务的运行态摘要保留，
管理界面和新接口逐步切换到独立发布单。

## Compose 更新

Agent 只允许访问显式配置的 Compose 根目录，不挂载或扫描整个宿主机文件系统。
建议通过 `CLOUDHELM_AGENT_COMPOSE_ROOTS` 配置允许目录，并以读写方式将这些目录
映射到 Agent。

例如业务 Compose 位于宿主机 `/srv/ai-services`：

```yaml
services:
  agent:
    volumes:
      - /srv/ai-services:/srv/ai-services
```

```dotenv
CLOUDHELM_AGENT_COMPOSE_ROOTS=/srv/ai-services
```

必须保持容器内外绝对路径一致，以便 Compose v2 容器标签中的配置文件路径可以
被安全解析。该变量默认为空，此时 Compose 管理的容器升级会在停止旧容器前拒绝。

更新步骤：

1. 根据 Compose 标签定位项目、service 和实际定义 `image` 的配置文件。
2. 确认文件位于允许目录内，并且 service 唯一。
3. 拉取目标镜像，确认新旧镜像仓库相同。
4. 备份原文件，生成候选文件并执行 `docker compose config` 校验。
5. 通过临时文件、`fsync` 和原子重命名修改 `image`。
6. 原位切换容器；失败时恢复旧容器和旧 Compose。
7. 业务健康验证失败时，由发布状态机下发回滚任务，恢复容器和 Compose。

多 Compose 文件或 override 文件无法唯一确定镜像来源时必须停止，不能猜测修改。

## 单本地实例发布流程

1. 创建独立的临时 ACS Deployment，固定运行升级前的旧镜像。
2. 等待保护实例 Ready、完成业务上报并进入网关路由。
3. 在本地实例继续服务时预拉取目标镜像并校验 Compose。
4. 将本地实例置为 `draining`，统一网关立即摘除该路由。
5. 等待业务上报 `accepting=false` 且 `active_businesses=0`。
6. 原子更新 Compose 并切换本地容器。
7. 等待 Docker Health 与重启后的业务 Ready 上报。
8. 恢复本地接单，并将高负载 ACS 模板更新为新 Tag。
9. 排空、删除旧版本保护实例，完成发布。

保护实例未正常服务前不得排空本地实例；本地新版本未恢复服务前不得关闭保护
实例。

## 多本地实例发布流程

发布开始时完成全量预检查，并尽可能在各节点预拉取目标镜像。随后按固定顺序
逐个执行：

1. 当前实例进入 `draining`，从网关路由摘除。
2. 等待停止接单且在途业务归零。
3. 更新 Compose 和容器。
4. 等待 Docker 与业务健康验证。
5. 恢复 `serve`，再处理下一个实例。

某个实例失败时自动恢复该实例，停止后续步骤。已经升级并验证成功的实例继续
服务，管理员可以重试当前步骤或对整批发布发起回滚。

## 维护状态

实例状态扩展为：

- `serve`：正常接单。
- `draining`：已从网关摘除，等待业务停止接单和清空在途任务。
- `maintenance`：已经排空，可以人工维护。
- `restoring`：维护结束，等待健康恢复。
- `failed`：维护或恢复失败。

进入维护后，网关发现接口不再返回该实例；业务程序通过上报响应获得期望状态。
只有在重新上报 `healthy=true`、`ready=true`、`accepting=true` 后，退出维护的实例
才重新加入网关。

## 独立弹性事件

实例池和事件类型分开记录：

- `acs_release`：某次升级专用的旧版本保护实例。
- `acs_load`：由业务负载触发的常规弹性实例。
- `acs_failover`：本地故障兜底实例。

对应事件使用 `release_guard_scale_up/down`、`load_scale_up/down` 和
`failover_scale_up/down`。升级保护池不参与高负载伸缩的副本数、窗口和冷却时间
计算，高负载伸缩也不得回收升级保护实例。

保护 Pod 中会注入 `CLOUDHELM_INSTANCE_POOL=acs_release` 和
`CLOUDHELM_RELEASE_ID=<发布单 ID>`。业务上报客户端必须将前者作为 `pool`，并在
`metadata.release_id` 回传后者；平台只有在该实例健康、接单并已注册网关地址后，
才会排空唯一的本地实例。

## 管理界面

发布详情以步骤时间线展示预检查、保护实例、逐个排空、Compose 更新、容器切换、
业务验证和保护实例回收。每个本地实例显示当前/目标 Tag、Compose 状态、在途业务、
Docker Health、业务 Ready、耗时和错误。

操作包括开始升级、暂停后续实例、重试、取消未执行部分、选择历史版本回滚、
进入维护和退出维护。
